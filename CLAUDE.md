# Korzinka Business

B2B wholesale order-management system for Korzinka. Replaces phone-based manual ordering with a role-driven workflow: **sales managers** take orders from corporate clients, **store managers** approve and drive order state forward, **pickers** collect items at a branch, **SCM** chases backorders from the main Korzinka warehouse, **accountants** gate on payment, **admin** oversees everything.

Single NestJS monolith. Primary UI is an internal admin dashboard whose center of gravity is a **Kanban board of orders** (each column = status, each card = order, every state transition written to an audit log). Supporting pages: **Staff**, **Products**, **Branches**, **Customers**, **Orders** detail.

## Maintaining This File

AGENTS.md is the contract between this codebase and any AI assistant working on it. **It must stay in sync with the code.** When you make a change that a future contributor (human or AI) would need to know to avoid breaking something or duplicating effort, update this file in the same change set.

**Keep `AGENTS.md` and `CLAUDE.md` identical.** They are the concise project-pattern guide for coding agents — different assistants read one or the other, but both must see the same content. Every edit to either file must be mirrored to the other in the same change set (`cp CLAUDE.md AGENTS.md` after editing one, or vice versa). Drift between the two means whichever assistant reads the stale copy will work from outdated rules.

**Always update AGENTS.md when you:**

- Add, rename, or remove an HTTP endpoint, or change its auth/role/role-scoped behavior → update the relevant API table
- Change a request/response shape, query-param filter, or pagination contract → update the endpoint row
- Change an entity (new column, type/precision change, new index, new constraint) → update the matching row in the directory reference, plus any "Gotchas" line that referenced the old type
- Add or remove a feature module → update the Module Map and Directory Reference
- Add a new shared utility, decorator, pipe, or pattern that other code should reuse → add it under "Patterns To Follow" (with the *why*) and to the Directory Reference
- Change the order lifecycle, transition matrix, or per-transition role gating → update the Order Lifecycle section and the transition table
- Change environment variables, bootstrap behavior, or any startup precondition → update Stack / Common Commands / Gotchas
- Discover a non-obvious behavior, footgun, or constraint → add it to Gotchas with a one-line *why*
- Apply a migration that changes column types, indexes, or enums → update the directory reference for the affected entity

**Don't** update AGENTS.md for:

- Pure refactors that preserve all of the above (renamed local variable, extracted private helper, reformatted code) — the code is the source of truth for those
- Bug fixes that don't change the API/schema/behavior contract
- Work-in-progress on a branch that hasn't merged yet

**Keep entries dense.** This file is loaded into every assistant's context — every line costs tokens. Prefer one tight sentence with the rule + reason over a paragraph. If a section grows past its utility, prune it; stale docs are worse than missing docs.

**Always append to the Changelog** at the bottom when you make a change covered by the bullets above. Date format: `YYYY-MM-DD`. One bullet per logical change, ordered newest first.

## Business Context

- ~100 orders/day across all branches, ~10k SKUs in catalog, 10 operators
- Multi-branch / multi-region; many entities are branch-scoped (staff assignments, orders, delivery threshold)
- Minimum order **500,000 UZS**; delivery free above per-branch `deliveryThreshold` (default 500k UZS), Yandex B2B API later
- Some line items may be backordered from the main Korzinka warehouse (2–3 day lead time) — partial fulfillment is a first-class state (`PARTIAL`), not an error
- Bilingual **RU/UZ** — product names are stored as `{ uz, ru }` jsonb and resolved in the view/notification layer
- Phase 1: no client self-service; clients only receive delivery/tracking notifications

## Roles

Seven roles defined in [user-role.enum.ts](src/common/enums/user-role.enum.ts): `BASIC`, `ADMIN`, `SALES_MANAGER`, `STORE_MANAGER`, `SCM`, `ACCOUNTANT`, `PICKER`. Users are assigned to branches via the [UserBranch](src/branches/entities/user-branch.entity.ts) join entity (composite PK `userId + branchId`).

| Role            | Scope                         | Responsibility |
|-----------------|-------------------------------|----------------|
| `admin`         | Cross-region, cross-branch    | Full control: staff, catalog, branches, customers, cross-branch Kanban visibility |
| `accountant`    | Multi-branch, multi-region    | Payment gate, post-delivery AR, invoicing *(not yet implemented)* |
| `sales_manager` | Multi-branch, multi-region    | Creates orders, manages customers, routes orders to the right branch, can cancel |
| `store_manager` | Single branch                 | Drives the state machine: confirms, starts collection, marks READY / PARTIAL, completes |
| `picker`        | Single branch                 | Assigned on `CONFIRMED → IN_COLLECTION` transition; physically collects items |
| `scm`           | Cross-branch (supply chain)   | Backorder queue from main warehouse: per-item ETA, arrival mark *(not yet implemented)* |

> Role × branch permission checks (`hasPermission(userId, action, branchId)`) are **not yet wired** — the `RolesGuard` currently checks role only. Transition-level gating is implemented via the `ORDER_TRANSITION_ROLES` map in [orders.constants.ts](src/common/constants/orders.constants.ts). Don't silently broaden existing `@Roles(...)` guards — confirm intended permission with the user before changing a handler's guard.

## Order Lifecycle

```
DRAFT ──┐→ CONFIRMED ──┐→ IN_COLLECTION ⇄┬→ READY ──→ COMPLETED
        ↓              ↓                 ⇅↘ PARTIAL ──→ READY
        CANCELLED ←────┴─────────────────/
```

`READY` can step back to `IN_COLLECTION` (no payload, retains the existing picker) or to `PARTIAL` (requires `backorderedItems`, mirroring `DRAFT → CONFIRMED`). Both reverse paths are gated to `ADMIN`, `STORE_MANAGER`, `SALES_MANAGER`.

Implemented in [orders.service.ts](src/orders/orders.service.ts) with the transition matrix in [orders.constants.ts](src/common/constants/orders.constants.ts). Statuses: [order-status.enum.ts](src/common/enums/order-status.enum.ts).

- **Order code** `KB-{BRANCH}-{YEAR}-{NNNN}` — generated on transition `DRAFT → CONFIRMED` via `MAX(code) + 1` per branch/year prefix, *not* on insert
- **Backorders-first confirm** — `OrderItem.status` defaults to `AVAILABLE` on create. `DRAFT → CONFIRMED` accepts an **optional** `backorderedItems: [{ itemId, backorderedQuantity }]`. Listed items flip to `BACKORDERED` with their quantity; unlisted items stay/flip to `AVAILABLE` with `backorderedQuantity = 0`. The transition **always** flips the order to `CONFIRMED` and generates `code = KB-{BRANCH}-{YEAR}-{NNNN}` — there is no short-circuit back to `DRAFT`. Omit/empty `backorderedItems` when everything is in stock
- **Picker assignment** — `CONFIRMED → IN_COLLECTION` requires `pickerId` in the transition payload; the picker's role must be `PICKER`. The order can have BACKORDERED items and still transition — they carry through to picking
- **PARTIAL (auto from item status)** — `IN_COLLECTION → PARTIAL` takes **no payload** for backorder declaration. The transition is allowed only when the order has ≥1 active item currently in `BACKORDERED` status (set at confirm time or via the item-edit endpoint); otherwise 400. Passing `backorderedItems` on this transition is a 400 — declare backorders earlier
- **Order-detail CRUD without a transition** — `PATCH /orders/:id/details`, `POST /orders/:id/items`, `PATCH /orders/:id/items/:itemId`, and `DELETE /orders/:id/items/:itemId` (roles `ADMIN`, `SALES_MANAGER`, `STORE_MANAGER`) are allowed in `DRAFT`, `CONFIRMED`, `IN_COLLECTION`, `PARTIAL`, and `READY`; `COMPLETED` / `CANCELLED` return 400. Item delete is soft-delete (`OrderItem.deletedAt`), the last active item cannot be deleted, and changing product means delete old line + add a new line. Successful item mutations recompute `Order.totalAmount`; for bank-payment orders they notify accountants via `payment.recheck_required`
- **PAID orders block basket-composition and quantity edits — but stock-state edits stay open** — once `paymentStatus = PAID`, `POST /orders/:id/items`, `DELETE /orders/:id/items/:itemId`, and any `PATCH /orders/:id/items/:itemId` that sends `quantity` return 400 (`Item quantity cannot be changed while the order is PAID; backorder status edits are still allowed.` for the PATCH; `Order items cannot be changed while the order is PAID; unmark paid first via POST /orders/:id/unmark-paid` for add/delete). Backorder-only PATCHes — `status` flips between `AVAILABLE` and `BACKORDERED`, `backorderedQuantity` adjustments, and `notes` riding along — remain open on PAID orders so picker/SCM can track stock state without round-tripping through `unmark-paid`. `quantity * discountedPrice` is the only contributor to `totalAmount`, so backorder-only edits cannot move the amount and `payment.recheck_required` does not fire. `PATCH /orders/:id/details` (endDate) also remains open. To change quantity or basket composition on a paid order, ADMIN flips it via `POST /orders/:id/unmark-paid` (writes audit, pings accountants), then edits, then re-marks via `POST /orders/:id/mark-paid`. There is no automatic PAID→UNPAID reset on any item edit — the quantity lock is hard, and backorder edits never touch payment status
- **Cash/card mark-paid is gated to `status = READY`** — `POST /orders/:id/mark-paid` for `paymentType ∈ {CASH, CARD}` returns 400 unless `order.status = READY`. Bank orders (`BANK_PREPAYMENT`, `BANK_POST_PAYMENT`) keep their any-status mark-paid behavior. The same constraint applies to `POST /orders` `paymentStatus='paid'`: it's now bank-only at create time (cash/card creates always start UNPAID and must reach READY before being marked PAID). Symmetrically, a paid cash/card order in READY cannot revert to `IN_COLLECTION` or `PARTIAL` — see Reverse READY transitions below
- **Backorder item edits** — `PATCH /orders/:id/items/:itemId` accepts `status` / `backorderedQuantity` only while the order is `CONFIRMED`, `IN_COLLECTION`, or `PARTIAL`. Three supported operations: full resolve (status=AVAILABLE forces `backorderedQuantity=0`), re-flag an available item (status=BACKORDERED with a quantity), reduce/adjust the pending amount (`backorderedQuantity` only, item must already be BACKORDERED). SCM is notified via `backorder.updated` only when backorder status/quantity changes or a BACKORDERED item is deleted. SCM is **also** added to the `order.details_updated` recipient list on `addItem` and `deleteItem` (regardless of stock status), so item-composition changes always reach the warehouse
- **PARTIAL → READY (backorder resolution)** — `PARTIAL → READY` accepts `arrivedItemIds: string[]` as a bulk convenience. Each listed active item must currently be `BACKORDERED` and belong to the order; they're flipped to `AVAILABLE` with `backorderedQuantity = 0` inside the same transaction. The transition is then blocked if **any** active item is still `BACKORDERED` — so the call either resolves every remaining backorder or fails. Individual resolution can also happen via the item-edit endpoint
- **Reverse transitions** — `READY → IN_COLLECTION`, `READY → PARTIAL`, and `PARTIAL → IN_COLLECTION` (all gated to `ADMIN`, `STORE_MANAGER`, `SALES_MANAGER`) let operators recover from a premature READY or PARTIAL mark. `READY → IN_COLLECTION` takes no payload by default and retains `order.pickerId` (passing a new `pickerId` reassigns); the existing `order.assigned_to_picker` notification fires for the (possibly new) picker. `READY → PARTIAL` requires `backorderedItems: [{ itemId, backorderedQuantity }]` (≥1) and reuses the `DRAFT → CONFIRMED` declaration path — listed items flip to `BACKORDERED`, unlisted items flip back to `AVAILABLE` with `backorderedQuantity = 0`, and the `STATUS_CHANGE` audit row carries the per-item diff. The existing `order.partial` notification trigger keys on `to === PARTIAL` so it fires for both forward and reverse paths. Reverting from READY does **not** reset `paymentStatus`: a previously PAID order stays PAID, but `READY → COMPLETED` still requires `PAID` so re-arriving in READY won't add a second payment step. `completedAt` is never set in READY, so no clearing is needed. Reverse paths are blocked for **PAID cash/card orders** — `OrderTransitionService` rejects `READY → IN_COLLECTION` and `READY → PARTIAL` with 400 (`READY → <to> is blocked for PAID cash/card orders. Unmark paid first via POST /orders/:id/unmark-paid`) when `paymentStatus = PAID` and `paymentType ∈ {CASH, CARD}`. Bank-paid orders are exempt (a paid bank order in `IN_COLLECTION`/`PARTIAL` is normal). Recovery is the same two-step as basket edits on a paid order: ADMIN calls `POST /orders/:id/unmark-paid`, runs the reverse, re-marks via `POST /orders/:id/mark-paid` once back in READY. `PARTIAL → IN_COLLECTION` takes no payload by default and retains `order.pickerId` (passing a new `pickerId` reassigns); existing `BACKORDERED` items stay BACKORDERED so the picker can keep resolving them via `PATCH /orders/:id/items/:itemId` from `IN_COLLECTION`, and the order can re-enter PARTIAL anytime since the `IN_COLLECTION → PARTIAL` rule (`≥1 BACKORDERED item`) still holds. Audit `STATUS_CHANGE` with `diff: null`. The existing `order.assigned_to_picker` notification fires for the (current or reassigned) picker. The cash/card-PAID block above only applies to reverse paths *out of READY*; cash/card mark-paid is gated to READY in the first place, so cash/card PAID + PARTIAL is unreachable
- **Discount** — resolved from `Customer.discountPercent` at item-build time; both `originalPrice` and `discountedPrice` are stored per line
- **Payment gate, returns, delivery** — not yet implemented. `PaymentType` on the order is copied from the customer's `paymentTerms` at creation. `Order.deliveryType` (`delivery` / `take_away`, default `delivery`) is captured at create but isn't wired into any dispatch logic yet
- **Audit** — every `create`, detail/item edit, payment mark, and `transition` writes an `AuditLog` row **inside the same `DataSource.transaction`** as the state write. Item CRUD audit rows use nested `items.<id>` objects with `operation`, `product`, and changed field entries; `STATUS_CHANGE` rows carry the same item-scoped shape when the transition itself mutated backorder state. The Kanban detail-pane timeline reads all of this via `GET /orders/:id/logs`

## UI Surfaces

The backend is an HTTP API; the admin dashboard is the sole frontend client in Phase 1.

- **Orders / Kanban dashboard** — one column per `OrderStatusEnum`. Card → detail pane showing items, customer, actions (role-gated transitions via `POST /orders/:id/transitions`), and the audit timeline (`GET /orders/:id/logs`)
- **Staff** (`/users`) — admin-only CRUD by `username`
- **Products** (`/products`) — catalog CRUD + XLSX bulk import (`POST /products/import`); list supports transliterated fuzzy search via pg_trgm
- **Branches** (`/branches`) — admin-only CRUD + `POST/DELETE /branches/:id/users/:userId` to assign/unassign staff
- **Customers** (`/customers`) — admin-only CRUD of corporate buyers
- **Bell menu / notifications drawer** — backed by `GET /notifications` (paginated history), `GET /notifications/unread-count` (badge), and live `notification.created` socket pings on the `/socket` namespace. Reads are scoped to the current user; the recipient row id is what `PATCH /notifications/:id/read` takes
- **Auth** (`/auth/login`, `/auth/me`) — JWT bearer; `login` is the only public route

> **Realtime delivery** — the dashboard opens **one** Socket.IO connection on namespace `/socket` (websocket-only) carrying a JWT in `handshake.auth.token`. The server emits a single event called `message` with a `{ type, payload, sentAt }` envelope; the client switches on `type` to handle order updates (`orders.changed`, `order.changed`) and notification pings (`notification.created`, `notifications.unread_count_changed`). HTTP remains the source of truth — the socket carries hints to refetch.

### Users (Staff) — [users.controller.ts](src/users/users.controller.ts)

Class-level `@Roles(UserRole.ADMIN)` — admin-only by default. `GET /users/pickers` overrides to also allow `STORE_MANAGER` (they pick the picker during `CONFIRMED → IN_COLLECTION`).

| Method | Path | Roles | Description |
|--------|------|-------|-------------|
| `POST`   | `/users` | `ADMIN` | Create a staff user (`name`, `username`, `password`, `role`). Username uniqueness enforced by unique index. Optional `branchIds: string[]` assigns the new user to those branches in the same transaction; branches must exist and be `isActive=true`. Missing/inactive ids return 400 with the offending ids/codes. Empty array = no assignments (same as omitting). `assignedBy` on each `UserBranch` row is the calling admin |
| `GET`    | `/users` | `ADMIN` | Paginated list. Filters: `role`, `branchId` (joins `user_branches`), `search` (ILIKE on `username` + `name`), `isActive`. List response is **lean** — does not include `branches` |
| `GET`    | `/users/pickers` | `ADMIN`, `STORE_MANAGER` | Paginated list of `PICKER`-role users with their **current workload** (`activeAssignmentsCount` = orders where `pickerId = user.id` AND `status = IN_COLLECTION`). Filters: `branchId`, `search`, `isActive`. Implemented as two queries — `users` page (≤ limit), then a single `GROUP BY pickerId` over `orders` filtered to the returned ids. Route is registered **before** `:id` so it doesn't get parsed as a UUID. Lean shape — does not include `branches` |
| `GET`    | `/users/:id` | `ADMIN` | Get one user by UUID. Response includes `branches: { id, name, code }[]` (sorted by `code`) — see note below |
| `PATCH`  | `/users/:id` | `ADMIN` | Update profile fields / role / `isActive`. Optional **delta** fields `addBranchIds: string[]` and `removeBranchIds: string[]` mutate the user's branch set in a single transaction. Both are **idempotent**: ids in `addBranchIds` already assigned are skipped (preserving existing `assignedAt`/`assignedBy`); ids in `removeBranchIds` not currently assigned are silently ignored. The two lists must not overlap (400 if they do). `addBranchIds` validates existence + `isActive=true` (same as `POST /users`); `removeBranchIds` does not require active branches (you can unassign from a soft-deleted branch). `assignedBy` on newly inserted rows is the calling admin |
| `DELETE` | `/users/:id` | `ADMIN` | Deactivate (soft delete — sets `isActive = false`). Existing `UserBranch` rows are preserved so re-activation doesn't require re-assignment |

> **Single-user response shape** — `POST /users`, `PATCH /users/:id`, `GET /users/:id`, and `DELETE /users/:id` include `branches: { id, name, code }[]` (sorted by `code`). `GET /users` and `GET /users/pickers` return the lean shape without `branches` to keep the page query cheap.

### Products — [products.controller.ts](src/products/products.controller.ts)

Read open to any authenticated user; writes are admin-only.

| Method | Path | Roles | Description |
|--------|------|-------|-------------|
| `POST`   | `/products` | `ADMIN` | Create a product. Conflict 409 if `sku` already exists |
| `POST`   | `/products/import` | `ADMIN` | `multipart/form-data` XLSX upload. Required form fields: `file` (binary) and `lang` (`uz` \| `ru`). Header row auto-detected. Columns `A=SKU, B=barcode, D=unit, F=name, G=price, H=brand`; columns `C`, `E`, and `I+` are ignored. Max 10 MB, validated by [`FileUploadPipe`](src/common/pipes/file-upload.pipe.ts). Returns `{ createdCount, updatedCount, skippedCount, skippedRows[] }`. **Per-language write:** new SKUs are created with `name = { uz: <text>, ru: '' }` (or vice versa for `lang=ru`) — only the side matching the request is populated. Existing SKUs get a patch update: `price`, the side matching `name[lang]`, and `barcode` (if the file row has one) are each updated only when they actually changed |
| `GET`    | `/products` | any authenticated | Paginated list. Optional `isActive` (boolean, parsed via `@TransformBoolean()`) filters by active flag. Optional `search` is **tokenized on whitespace** (≥2 chars/token). Each token is **routed by shape**: SKU-shaped tokens (regex `SKU_TOKEN_PATTERN` — `^[A-Za-z0-9-]+$` with ≥1 digit, e.g. `00002`, `162000001-00100`, `B-12`) match `product.sku ILIKE '%token%'`, `product.barcode ILIKE '%token%'`, **OR** the concatenated name expression via literal ILIKE substring (no fuzzy). All other tokens match the concatenated `name->>'uz' || ' ' || name->>'ru'` via ILIKE substring **or** `pg_trgm.strict_word_similarity > 0.4` over Cyrillic/Latin transliteration variants. Routing prevents numeric tokens from fuzzy-matching numeric *words* inside names (e.g. `00002` no longer scores against `'10 000 сум'` because `strict_word_similarity('00002','000') ≈ 0.5` was the noise generator). `strict_word_similarity` (not `word_similarity`) bounds the matched extent to word boundaries. Ranked by the **sum** of best per-token `strict_word_similarity` over name tokens; SKU/barcode-only queries (no name tokens) fall back to `sku ASC`. AND-across-tokens means a mixed query like `сыр 00002` requires both: name token via fuzzy/literal, SKU-shaped token via SKU/barcode-or-literal-name |
| `GET`    | `/products/:id` | any authenticated | Get one product |
| `PATCH`  | `/products/:id` | `ADMIN` | Update. Conflict 409 if new `sku` collides |
| `DELETE` | `/products/:id` | `ADMIN` | Soft-delete (`isActive = false`); the row is preserved so existing `OrderItem.product` FKs stay valid |

### Customers — [customers.controller.ts](src/customers/customers.controller.ts)

Read open to any authenticated user; create / update are open to every role except `PICKER` and `BASIC`. **No delete endpoint** — customers are referenced by orders (`onDelete: 'RESTRICT'`).

| Method | Path | Roles | Description |
|--------|------|-------|-------------|
| `POST`  | `/customers` | `ADMIN`, `SALES_MANAGER`, `STORE_MANAGER`, `SCM`, `ACCOUNTANT` | Create. Body takes `contractNumbers: string[]` (≥1 required, deduped within payload via `@ArrayUnique`). Conflict 409 only on `tin` / `sapId` collisions — contract numbers are unique **per customer**, so two customers may legitimately hold the same contract number. `sapId` and `contactPerson` are optional |
| `GET`   | `/customers` | any authenticated | Paginated list. Optional `search` runs **case-insensitive ILIKE** OR-matched against `companyName`, `tin` (INN), and `sapId`. Returns the **lean** `PublicCustomer` shape — no `contracts` array |
| `GET`   | `/customers/:id` | any authenticated | Get one customer. Includes `contracts: { id, contractNumber, isActive, createdAt }[]` sorted by `createdAt ASC` (so the original onboarding contract is index 0). Soft-deleted contracts (`isActive=false`) are returned alongside active ones; the client filters/renders as needed |
| `GET`   | `/customers/:id/contracts` | any authenticated | List a customer's contracts as a flat array (not paginated). Optional `isActive` query param (boolean, parsed via `@TransformBoolean()`) filters to active/inactive only; omit to return both. Sorted by `createdAt ASC`. Returns the same `{ id, contractNumber, isActive, createdAt }` shape that `GET /customers/:id` exposes inline. Order-create UI fetches `?isActive=true` to populate the contract dropdown without paying for the full customer payload |
| `PATCH` | `/customers/:id` | `ADMIN`, `SALES_MANAGER`, `STORE_MANAGER`, `SCM`, `ACCOUNTANT` | Update scalar fields and/or mutate the contract list. `tin` / `sapId` re-checked for uniqueness on change. Pass `sapId: null` (or `contactPerson: null`) to clear. Optional **delta** fields `addContractNumbers: string[]` and `removeContractNumbers: string[]` mutate the contract set in a single transaction. Both are **idempotent**: numbers in `addContractNumbers` that are already active on this customer are silent no-ops; numbers that exist as **inactive** rows on this customer are **revived** (`isActive=true`, original `id`/`createdAt` preserved). Numbers in `removeContractNumbers` are **soft-deleted** (`isActive=false`); the row is kept for history and downstream FK stability. Numbers in `removeContractNumbers` not currently active on this customer are silently ignored. The two lists must not overlap (400 if they do). The post-apply **active** contract count must be ≥1 (400 with `Customer must have at least one active contract` otherwise — caller swapping the entire set must include at least one add). Cross-customer contract collisions on add are not a conflict (uniqueness is per-customer). Mirrors `PATCH /users/:id` `addBranchIds`/`removeBranchIds` shape and semantics |
| `POST`  | `/customers/:id/contracts` | `ADMIN`, `SALES_MANAGER`, `STORE_MANAGER`, `SCM`, `ACCOUNTANT` | **Secondary path** — primary contract-set mutation flow is via `PATCH /customers/:id` `addContractNumbers`/`removeContractNumbers`. Adds a single contract by `{ contractNumber }`, returning the resulting `{ id, contractNumber, isActive, createdAt }` (201). Revives an existing inactive row when one matches `(customerId, contractNumber)` (preserves `id`/`createdAt`); otherwise inserts a new row. **409** if the number is already active on this customer (this is the strict-add semantics divergence from PATCH — POST treats "already there" as a conflict, PATCH treats it as a no-op). Cross-customer collisions are silently allowed (uniqueness is per-customer). 404 on unknown customer |
| `DELETE`| `/customers/:id/contracts/:contractId` | `ADMIN`, `SALES_MANAGER`, `STORE_MANAGER`, `SCM`, `ACCOUNTANT` | **Secondary path** — primary contract-set mutation flow is via `PATCH /customers/:id` `removeContractNumbers`. Soft-deletes the row (`isActive=false`); the row is preserved for history and downstream FK stability. `204 No Content`. **400** if removing it would leave the customer with zero active contracts. **Idempotent on already-inactive rows** (also returns 204). 404 if the contract doesn't belong to this customer |

> **Single-customer response shape** — `POST /customers`, `PATCH /customers/:id`, and `GET /customers/:id` return `PublicCustomer` including `contracts: { id, contractNumber, isActive, createdAt }[]` (sorted by `createdAt ASC`, includes both active and soft-deleted rows). `GET /customers` returns the lean shape without `contracts` to keep the page query cheap. Same trade-off `users` makes for `branches`.

### Orders (Kanban) — [orders.controller.ts](src/orders/orders.controller.ts)

The heart of the system. List = Kanban feed; `:id/transitions` drives the Kanban drag; `:id/logs` renders the audit timeline in the detail pane.

| Method | Path | Roles | Description |
|--------|------|-------|-------------|
| `POST`  | `/orders` | every role except `PICKER` and `BASIC` (`ADMIN`, `SALES_MANAGER`, `STORE_MANAGER`, `SCM`, `ACCOUNTANT`) | Create an order. Rejects with 400 if `endDate < now`. Validates customer + branch existence, **requires `contractId` referencing one of `customerId`'s active contracts** (400 with a contract-specific message if the contract belongs to a different customer or is not active — validated against the already-loaded `customer.contracts` so no extra DB query), builds `OrderItem`s with `Customer.discountPercent` applied, copies `paymentType` from customer, stamps `deliveryType` from payload (defaults to `DELIVERY`), defaults `paymentStatus = UNPAID`, writes the `CREATE` audit row — all in one `DataSource.transaction`. Starts in `DRAFT` status, `code` is still null. Optional `paymentStatus = 'paid'` in the body marks the order PAID at creation, but is **bank-only** (`BANK_PREPAYMENT` / `BANK_POST_PAYMENT`) — passing it on a cash/card order returns 400 (`Cash/card orders cannot be created with paymentStatus=paid; mark PAID after the order reaches READY`). For bank orders, the role gate is `ADMIN` / `ACCOUNTANT`. On success this writes a second `UPDATE` audit row in the same transaction with `paymentStatus: { from: 'unpaid', to: 'paid' }` so the timeline shows the explicit mark-paid event. The actor's `id` is recorded as `salesManagerId` regardless of role (the column is the "who created this order" pointer) |
| `GET`   | `/orders` | any authenticated | Paginated Kanban feed. Implemented as two queries: the orders page, then a single `GROUP BY orderId` over active `order_items` filtered to `status = BACKORDERED` for the returned ids. Ordered by `updatedAt DESC` (rows surface to the top of the Kanban whenever they're touched — created, edited, transitioned, or item statuses changed) |
| `GET`   | `/orders/:id` | any authenticated | Full detail — includes active `items.product` (soft-deleted items excluded), all relations — for the Kanban detail pane |
| `GET`   | `/orders/:id/logs` | any authenticated | The order's `AuditLog` timeline (joined with `actor`), ordered `createdAt DESC` (newest first). Powers the status-change log in the detail pane |
| `PATCH` | `/orders/:id/details` | `ADMIN`, `SALES_MANAGER`, `STORE_MANAGER` | Edit `endDate` only. No-op same-date calls return the order without audit/socket/notification. Successful edits write `UPDATE` audit diff `{ endDate: { from, to } }`, bump `updatedAt`, emit `detailsUpdated`, and notify admins + the order's sales manager + branch store managers |
| `POST`  | `/orders/:id/transitions` | varies per transition — see [`ORDER_TRANSITION_ROLES`](src/common/constants/orders.constants.ts) | Drive the state machine. Body: `{ nextStatus, pickerId?, backorderedItems?, arrivedItemIds?, notes? }`. Validates against `ALLOWED_ORDER_TRANSITIONS`, runs the side-effects for the target state (see below), saves the new status, writes a `STATUS_CHANGE` audit row — all in one transaction. **Payment-status gate:** `READY → COMPLETED` requires `order.paymentStatus = PAID` (mark via `POST /orders/:id/mark-paid`); attempting it on an `UNPAID` order is a 400 regardless of `paymentType` |
| `POST`  | `/orders/:id/mark-paid` | role gated **per `paymentType`**: bank (`BANK_PREPAYMENT` / `BANK_POST_PAYMENT`) → `ADMIN`, `ACCOUNTANT`; cash/card → every role except `PICKER` and `BASIC` (`ADMIN`, `SALES_MANAGER`, `STORE_MANAGER`, `SCM`, `ACCOUNTANT`) | Flip `order.paymentStatus` from `UNPAID` to `PAID`. The controller's `@Roles(...)` is the **union** of both lists; the per-paymentType narrowing is enforced inside `OrdersService.markPaid` via `resolveMarkPaidRoles(paymentType)`, so a `STORE_MANAGER` calling this on a bank-paid order gets a `ForbiddenException` (not a generic role-guard reject). **Status gate:** cash/card orders return 400 unless `order.status = READY` (`Cash/card orders can only be marked PAID in status READY (current: <status>)`); bank orders accept any status (BANK_PREPAYMENT is typically marked at DRAFT/CONFIRMED, BANK_POST_PAYMENT later). 400 if the order is already `PAID`. Writes an `UPDATE` audit row with `paymentStatus: { from: 'unpaid', to: 'paid' }` in a single transaction |
| `POST`  | `/orders/:id/unmark-paid` | `ADMIN` only | Reverse a `mark-paid` — flips `order.paymentStatus` from `PAID` back to `UNPAID` so a paid order can be edited (item add/update/delete are blocked while PAID). 400 if the order is already `UNPAID`. Writes an `UPDATE` audit row with `paymentStatus: { from: 'paid', to: 'unpaid' }` and pings global `ACCOUNTANT` via `payment.unmarked` so they know to expect a re-marking. Emits socket action `paymentMarkedUnpaid` |
| `POST`  | `/orders/:id/items` | `ADMIN`, `SALES_MANAGER`, `STORE_MANAGER` | Add one active item. Body uses `CreateOrderItemDto` (`productId`, `quantity`, `originalPrice?`). Allowed in `DRAFT`, `CONFIRMED`, `IN_COLLECTION`, `PARTIAL`, `READY` **and only when `paymentStatus = UNPAID`** — PAID orders return 400 (use `POST /orders/:id/unmark-paid` first). Rejects inactive/unknown products and duplicate active `productId` on the order. Creates a fresh row even if the same product was previously soft-deleted. Recomputes `totalAmount`, writes item-scoped audit with `operation='add'`, emits `itemAdded`, and applies the order-detail notification/payment rules |
| `PATCH` | `/orders/:id/items/:itemId` | `ADMIN`, `SALES_MANAGER`, `STORE_MANAGER` | Edit an active order item's `quantity` and/or backorder state. Body `{ quantity?, status?, backorderedQuantity?, notes? }`; at least one of `quantity` / `status` / `backorderedQuantity` is required. Allowed in `DRAFT`, `CONFIRMED`, `IN_COLLECTION`, `PARTIAL`, `READY`. **PAID-order behavior is split:** any payload that includes `quantity` returns 400 while `paymentStatus = PAID` (unmark-paid first); backorder-only payloads (`status` / `backorderedQuantity` / `notes`) are accepted on PAID orders so picker/SCM can track stock state without flipping payment. `status` / `backorderedQuantity` are only accepted in `CONFIRMED`, `IN_COLLECTION`, `PARTIAL`. Quantity must be >0, and any BACKORDERED line must keep `backorderedQuantity ≤ quantity`. No-op calls skip audit/socket/notifications. Successful edits recompute `totalAmount` (no-op when only backorder fields changed), write item-scoped audit with `operation='update'`, emit `itemUpdated`, and apply notification/payment rules |
| `DELETE` | `/orders/:id/items/:itemId` | `ADMIN`, `SALES_MANAGER`, `STORE_MANAGER` | Soft-delete one active item by setting `OrderItem.deletedAt`; rejects deleting the last active item. Allowed in `DRAFT`, `CONFIRMED`, `IN_COLLECTION`, `PARTIAL`, `READY` **and only when `paymentStatus = UNPAID`**. Recomputes `totalAmount`, writes item-scoped audit with `operation='delete'` and `deletedAt`, emits `itemDeleted`, and applies notification/payment rules. Does **not** auto-transition `PARTIAL → READY` |

**Transition payload requirements** (enforced in `OrdersService.transition` → `applyTransitionSideEffects`):

| From → To | Roles | Required payload | Side-effect |
|-----------|-------|------------------|-------------|
| `DRAFT → CONFIRMED` | `ADMIN`, `SCM` | `backorderedItems: [{ itemId, backorderedQuantity }]` (optional); `notes?: string` is also accepted (optional) and flows into the audit row | Listed items → `BACKORDERED` with their quantity; unlisted → `AVAILABLE` with 0. Order always flips to `CONFIRMED` + generates `code = KB-{BRANCH}-{YEAR}-{NNNN}`. STORE_MANAGER cannot perform this transition — confirmation is reserved for ADMIN and SCM (warehouse) |
| `DRAFT → CANCELLED` | `ADMIN`, `SALES_MANAGER` | — | — |
| `CONFIRMED → IN_COLLECTION` | `ADMIN`, `STORE_MANAGER` | `pickerId` | Verifies user exists and has `role = PICKER`, sets `order.pickerId` |
| `CONFIRMED → CANCELLED` | `ADMIN`, `SALES_MANAGER` | — | — |
| `IN_COLLECTION → READY` | `ADMIN`, `STORE_MANAGER` | — | Fails if any item is still `BACKORDERED` |
| `IN_COLLECTION → PARTIAL` | `ADMIN`, `STORE_MANAGER` | — (declare backorders at confirm time or via item-edit endpoint) | Allowed only if the order currently has ≥1 item in `BACKORDERED` status; otherwise 400. Passing `backorderedItems` here is a 400 |
| `IN_COLLECTION → CANCELLED` | `ADMIN`, `SALES_MANAGER` | — | — |
| `PARTIAL → READY` | `ADMIN`, `STORE_MANAGER`, `SALES_MANAGER` | `arrivedItemIds: string[]` (each id must currently be `BACKORDERED` on this order) | Flips listed items → `AVAILABLE` with `backorderedQuantity = 0`; fails if any item is still `BACKORDERED` after resolution |
| `PARTIAL → IN_COLLECTION` | `ADMIN`, `STORE_MANAGER`, `SALES_MANAGER` | — (optional `pickerId` to reassign) | Reverse path. With no payload the order keeps its existing `pickerId`; passing `pickerId` validates the user (must have role `PICKER`) and reassigns. `BACKORDERED` items stay BACKORDERED — resolve individually via `PATCH /orders/:id/items/:itemId`, or let the order bounce back to PARTIAL via the `≥1 BACKORDERED item` rule. No diff written |
| `PARTIAL → CANCELLED` | `ADMIN`, `SALES_MANAGER` | — | — |
| `READY → COMPLETED` | `ADMIN`, `STORE_MANAGER` | — | Requires `order.paymentStatus = PAID`; otherwise 400 (`Order must be marked PAID before READY → COMPLETED`). Stamps `order.completedAt = now()` |
| `READY → IN_COLLECTION` | `ADMIN`, `STORE_MANAGER`, `SALES_MANAGER` | — (optional `pickerId` to reassign) | Reverse path. With no payload the order keeps its existing `pickerId`; passing `pickerId` validates the user (must have role `PICKER`) and reassigns. The same item-edit endpoint becomes available again once the order is back in `IN_COLLECTION`. No diff written. Blocked with 400 if `paymentStatus = PAID` and `paymentType ∈ {CASH, CARD}` — unmark-paid first |
| `READY → PARTIAL` | `ADMIN`, `STORE_MANAGER`, `SALES_MANAGER` | `backorderedItems: [{ itemId, backorderedQuantity }]` (≥1 required) | Reverse path. Mirrors `DRAFT → CONFIRMED`: listed items flip to `BACKORDERED` with the given quantity, unlisted items flip back to `AVAILABLE` with `backorderedQuantity = 0`. Empty/omitted payload is a 400 (READY orders have no `BACKORDERED` items by definition, so the inline declaration is the only way to land in PARTIAL). Audit `STATUS_CHANGE` row carries the `items.<id>` diff entries. Blocked with 400 if `paymentStatus = PAID` and `paymentType ∈ {CASH, CARD}` — unmark-paid first |

Any other `from → to` pair is rejected with `BadRequestException` (`Transition X → Y is not allowed`). Any allowed transition attempted by a role outside its row in the matrix is rejected with `ForbiddenException`. The `READY → COMPLETED` row is **payment-status-gated** (not role-gated by paymentType): every order — bank or cash/card — must be flipped to `paymentStatus = PAID` via `POST /orders/:id/mark-paid` first; the role split between bank and cash/card lives entirely on the mark-paid endpoint, so `READY → COMPLETED` itself stays uniformly `ADMIN` / `STORE_MANAGER`.

### Realtime — [socket.gateway.ts](src/socket/socket.gateway.ts)

Single Socket.IO namespace `/socket`, websocket-only transport, JWT-authenticated. Server emits one event called `message` carrying a `{ type, payload, sentAt }` envelope; client switches on `type`.

**Connecting:** pass JWT in `socket.handshake.auth.token`, or as `Authorization: Bearer <token>` on the handshake. Invalid/missing token → `client.disconnect(true)`. Token validation goes through the same [`AuthService.authenticateAccessToken`](src/auth/auth.service.ts) helper as the HTTP `JwtAuthGuard`.

**Rooms joined on connect:**
- `user:<userId>` — always (target for per-user notification pings)
- `role:<role>` — always (reserved for future role-targeted broadcasts)
- `orders:all` — only when role is **not** `BASIC`

**Client-emitted events** (all rooms scoped to the connecting socket):

| Event | Body | Effect |
|-------|------|--------|
| `order.watch` | `{ orderId: string }` | Joins `orders:<orderId>` to receive `order.changed` for that one order (used by the open detail pane) |
| `order.unwatch` | `{ orderId: string }` | Leaves `orders:<orderId>` |

**Server-emitted `message.type` values** (envelope is always `{ type, payload, sentAt }`):

| `type` | Room | Payload | Trigger |
|--------|------|---------|---------|
| `orders.changed` | `orders:all` | `OrderSocketPayload` (`{ action, orderId, branchId, actor, previousStatus?, nextStatus?, card }`) — `card` is the trimmed `OrderListItemDto` matching `GET /orders` | Any successful `OrdersService` mutator (`create`, `updateDetails` non-noop, `addItem`, `updateItem` non-noop, `deleteItem`, `transition`, `markPaid`). Emitted **after** the DB transaction commits |
| `order.changed` | `orders:<orderId>` | Same `OrderSocketPayload` | Same triggers as `orders.changed` — sent in addition for any client that ran `order.watch` for this id |
| `notification.created` | `user:<userId>` | `NotificationSocketPayload` (`{ id, notificationId, type, entityType, entityId, title, body, data, createdAt, unreadCount }`) — `id` is the recipient row id | Any `NotificationsService.notify(...)` writes inside an `OrdersService` mutator's transaction; one event per resolved recipient. Emitted **after** the transaction commits |
| `notifications.unread_count_changed` | `user:<userId>` | `{ unreadCount: number }` | Whenever the user's unread count changes — fires alongside every `notification.created` to that user, and from `PATCH /notifications/:id/read` (when an actual flip happened) and `PATCH /notifications/read-all` (when ≥1 row updated) |

**Notification triggers from `OrdersService`** (each row writes notification rows inside the transaction; socket pings fire after commit):

| `type` | Trigger | Recipient rule |
|--------|---------|----------------|
| `order.created` | end of `OrdersService.create` (always) | global `SCM` |
| `payment.required` | end of `OrdersService.create`, only when `paymentType ∈ { BANK_PREPAYMENT, BANK_POST_PAYMENT }` AND `paymentStatus = UNPAID` (i.e. not pre-marked PAID at create) | global `ACCOUNTANT` |
| `order.confirmed` | inside `transition`, `DRAFT → CONFIRMED` (always) | `STORE_MANAGER` at `order.branchId` |
| `backorder.created` | inside `transition`, `DRAFT → CONFIRMED` when ≥1 active item flips to `BACKORDERED` (counted via `STATUS_CHANGE` itemDiff) | global `SCM` |
| `order.details_updated` | inside `updateDetails`, `addItem`, `updateItem`, or `deleteItem` when a real change occurred | global `ADMIN` + the order's `salesManagerId` + `STORE_MANAGER` at `order.branchId`; **also global `SCM` when the trigger is `updateDetails`, `addItem`, or `deleteItem`** so the warehouse hears about endDate shifts and item-composition changes (only `updateItem` quantity/status edits keep the narrower recipient set, since backorder-relevant ones already reach SCM via `backorder.updated`) |
| `backorder.updated` | inside `updateItem` when backorder status/quantity changes, or inside `deleteItem` when the deleted active item was `BACKORDERED` | global `SCM` |
| `payment.recheck_required` | inside `addItem`, `updateItem`, or `deleteItem` when `totalAmount` changes on a bank-payment order. (PAID orders are blocked from these mutators upstream by `assertNotPaid`, so this only fires on UNPAID bank orders.) | global `ACCOUNTANT` |
| `payment.unmarked` | inside `unmarkPaid` (`POST /orders/:id/unmark-paid`) — admin-only reverse of `mark-paid` so a paid order can be edited | global `ACCOUNTANT` |
| `order.assigned_to_picker` | inside `transition`, `CONFIRMED → IN_COLLECTION` | the assigned `pickerId` |
| `order.partial` | inside `transition`, `IN_COLLECTION → PARTIAL` | the order's `salesManagerId` + global `SCM` + `STORE_MANAGER` at `order.branchId` |
| `order.ready` | inside `transition`, when target is `READY` (from either `IN_COLLECTION` or `PARTIAL`) | the order's `salesManagerId` + `STORE_MANAGER` at `order.branchId` |
| `payment.required_before_completion` | inside `transition`, when target is `READY` (from either `IN_COLLECTION` or `PARTIAL`) AND order is bank-paid AND `paymentStatus = UNPAID` | global `ACCOUNTANT` |
| `order.completed` | inside `transition`, `READY → COMPLETED` | the order's `salesManagerId` + global `ADMIN` |
| `payment.paid` | inside `markPaid`, only when the order's status was `READY` at the start of the call (captured before the transaction) | `STORE_MANAGER` at `order.branchId` |

The **actor is excluded** from every recipient set by default (so a store manager who confirms an order doesn't receive their own `order.confirmed` ping, and a sales manager who closes their own order doesn't receive their own `order.completed` ping even though `salesManagerId` is in the recipient list). Cross-branch roles (`ADMIN`, `SALES_MANAGER`, `ACCOUNTANT`, `SCM`) match globally; `STORE_MANAGER` and `PICKER` are **branch-narrowed** when `branchId` is provided in the recipient rule (so a payload combining `roles: [SCM, STORE_MANAGER]` + `branchId` resolves SCM globally and Store Managers only at the branch — matches `order.partial`). When a single rule mixes `userIds` with role-resolved ids, the union is deduped to one row per user. Inactive users are excluded.

## Module Map

Each feature module follows NestJS conventions: `*.module.ts`, `*.controller.ts`, `*.service.ts`, `dto/` (with `index.ts` barrel), `entities/` (with `index.ts` barrel).

**Implemented:**

- [auth/](src/auth/) — JWT login, [password.service.ts](src/auth/password.service.ts), `JwtAuthGuard` + `RolesGuard` registered as global `APP_GUARD` in [auth.module.ts](src/auth/auth.module.ts). Use `@Public()` to opt out of auth, `@Roles(UserRole.X)` to gate by role, `@CurrentUser()` to inject the authenticated user (shape in [authenticated-user.interface.ts](src/common/interfaces/authenticated-user.interface.ts))
- [users/](src/users/) — admin-only staff CRUD by `username`. [users-bootstrap.service.ts](src/users/users-bootstrap.service.ts) seeds the first admin from `INITIAL_ADMIN_*` env vars when the table is empty
- [products/](src/products/) — catalog CRUD + XLSX bulk import. `Product.name` is `{ uz, ru }` jsonb. Search uses `pg_trgm.word_similarity` + ILIKE over transliteration variants (Cyrillic ↔ Latin) generated in [transliteration.ts](src/common/text/transliteration.ts)
- [branches/](src/branches/) — Korzinka locations. Holds `code` (unique, freeform — stored as submitted, any non-empty string up to 20 chars), `deliveryThreshold`, `region`, `address`, `isDefault`. Explicit [UserBranch](src/branches/entities/user-branch.entity.ts) join entity for staff assignment
- [customers/](src/customers/) — corporate buyers: `companyName`, `tin` (unique), `sapId` (unique-when-set), `phone`, `paymentTerms`, `discountPercent`. Contract numbers live in the 1:N [CustomerContract](src/customers/entities/customer-contract.entity.ts) table (composite `UNIQUE(customerId, contractNumber)` over both active and inactive rows, cascade-on-customer-delete, `isActive` soft-delete flag) — every customer carries ≥1 **active** contract; two different customers may share the same number; removing a contract via `PATCH /customers/:id` flips `isActive=false`, re-adding revives the same row
- [orders/](src/orders/) — `Order` + `OrderItem` with full transition engine. `POST /orders/:id/transitions` drives the Kanban. See lifecycle above
- [audit/](src/audit/) — `AuditLog` write-only service. Called from `OrdersService` inside each transaction. `AuditService.write(em, payload)` takes the caller's `EntityManager` to join its transaction

## Patterns To Follow

- **DTOs validate at the boundary.** Everything in `dto/` uses `class-validator` + `@ApiProperty*`. `forbidNonWhitelisted` is on globally — unknown fields → 400
- **Boolean query params use `@TransformBoolean()`** from [transform-boolean.util.ts](src/common/utils/transform-boolean.util.ts). The global `ValidationPipe`'s implicit conversion treats any non-empty string as `true` (so `?isActive=false` would coerce to `true`) — this util parses `'true'/'false'/'1'/'0'` correctly
- **Temporal/date constraints live in DTO validators**, not services. See [`@IsNotInPast()`](src/common/validators/is-not-in-past.validator.ts) for the pattern: a `class-validator` custom decorator using `registerDecorator`. Keeps the rule reusable across DTOs (e.g. create + update share the same constraint without duplicating `if (date < Date.now())` in every service method)
- **Barrel files in `dto/` and `entities/`.** Every `dto/` and `entities/` subfolder needs an `index.ts` re-exporting siblings — imports use `from './dto'`, not per-file paths
- **List endpoints paginate.** Extend [PaginationQueryDto](src/common/dto/pagination-query.dto.ts), call [`buildPaginatedResponse`](src/common/utils/pagination.util.ts), return `PaginatedResponse<T>` (`data`, `meta: { page, limit, total, totalPages }`)
- **Swagger docs via `@ApiCustomResponse`.** The wrapper at [api-custom-response.decorator.ts](src/common/decorators/api-custom-response.decorator.ts) handles success shape (including `isPaginated`) and error schemas in one place — don't hand-roll `@ApiOkResponse` / `@ApiNotFoundResponse` per handler
- **Multi-row writes use `DataSource.transaction`.** See `OrdersService.create` / `update` / `transition`. Partial failures must roll back cleanly
- **Cross-module writes go through services, not repositories.** Callers pass the active `EntityManager` so downstream calls join the caller's transaction (see `AuditService.write(em, ...)`)
- **Business logic lives in services, not controllers.** Keep Kanban transition logic in `OrdersService` so future channels (bot, mobile) call the same path
- **Audit every state transition.** Order (and future customer/return/payment) state changes must write to `AuditLog` inside the same transaction as the state write — this is what the Kanban detail-pane timeline renders
- **Realtime hints + notification rows go through services, post-commit.** Notification rows are written **inside** the order's `dataSource.transaction` via [`NotificationsService.notify(em, ...)`](src/notifications/notifications.service.ts) (so they roll back atomically with the order write). Socket emits — both `SocketService.emitOrderChanged(...)` and `NotificationsService.emitAfterCommit(...)` — happen **after** the transaction resolves (never inside the callback; a rolled-back tx must not leak an event). No-op mutators (`updateDetails` with same `endDate`, `updateItem` with empty diff) must skip both the emit and the notify — mirror that diff short-circuit when adding a new mutator
- **Don't add backwards-compat shims for the socket payload shape.** The envelope `{ type, payload, sentAt }` is the contract; don't bolt on always-true booleans or aliases. If you need a new event, give it a new `type` and document it in the Realtime API section
- **Explicit join entities for M:N (and dedicated child entities for 1:N collections).** Never use `@JoinTable`; always create a dedicated class with a composite `@PrimaryColumn` (see `UserBranch`). For 1:N collections that the API needs to mutate by stable id, use a dedicated child entity with its own uuid PK rather than a Postgres array column (see `CustomerContract`) — this keeps `UNIQUE` enforcement native to PG and gives downstream FKs a stable target
- **Branch-scope queries** (future default). Except for admin / accountant / sales_manager cross-branch paths, list/read queries should constrain by the caller's accessible branch IDs. Not yet enforced — add the filter as the feature ships
- **Localize at the edge, not in entities.** `Product.name` is `{ uz, ru }` jsonb; resolve by recipient's preferred language inside the notification/view layer
- **Entities use UUID PKs, `timestamptz` timestamps, Postgres enums** (via `enum` column type). Don't change types without generating a migration
- **Migrations are the source of truth for schema.** `synchronize: false` in [typeorm-options.ts](src/database/typeorm-options.ts) and [data-source.ts](src/database/data-source.ts). After editing an entity, run `npm run migration:generate`, **rename `AutoMigration` → descriptive name** (both filename and class), review the diff before running
- **Register new entities in [entities.ts](src/database/entities.ts).** Missed registration means the table won't load into TypeORM
- **Errors:** throw Nest HTTP exceptions (`NotFoundException`, `BadRequestException`, `ForbiddenException`, `ConflictException`). TypeORM driver errors are translated by the global [TypeOrmExceptionFilter](src/common/filters/typeorm-exception.filter.ts) — don't catch them unless adding context
- **Gate routes with `@Roles(UserRole.X)` per handler** unless the entire controller is admin-only (e.g., `UsersController` applies it at the class level)
- **Path aliases:** use `@common/*` for anything under `src/common/`. Feature-to-feature imports use relative paths (`../branches/entities`). Don't mix styles within a file

## Gotchas

- `User.passwordHash` has `select: false`. To verify a password you must explicitly `addSelect('user.passwordHash')` — see [auth.service.ts:25-32](src/auth/auth.service.ts#L25-L32)
- The app won't start with a usable login if `INITIAL_ADMIN_*` env vars are missing **and** the users table is empty — `UsersBootstrapService` logs a warning and login will have no valid user
- Order `code` is **nullable** and unique only via a partial index (`WHERE "code" IS NOT NULL`) — DRAFT orders legitimately have `code = null` until confirmed. Don't add a `NOT NULL` constraint
- `OrderItem` uses TypeORM soft-delete (`deletedAt`) for order-detail item removal. Order reads, totals, backorder counts, and transition checks must operate on active rows only (`deletedAt IS NULL`); never hard-delete order items from mutators because audit logs and product FKs rely on stable line ids
- **PAID orders block quantity/basket-composition edits, but allow backorder-only edits.** `addItem` and `deleteItem` call `OrderLineService.assertNotPaid(order)` after `assertOrderDetailsEditable` and 400 if `paymentStatus = PAID`. `updateItem` instead calls `OrderLineService.assertQuantityNotChangedWhilePaid(order, dto.quantity)`, which only throws when `quantity` is present in the payload — pure backorder PATCHes (`status` / `backorderedQuantity` / `notes`) pass through. There is **no** automatic PAID→UNPAID reset on any item edit (quantity-bearing or not); recovery from a basket mistake is explicit via `POST /orders/:id/unmark-paid` (ADMIN-only). Don't add a "if PAID, auto-reset" branch back into `applyTotalAndPaymentDiff` (operations want the two-step) and don't add an auto-unpaid branch on backorder-edit-induced state either — the lock is intentionally one-directional (quantity locked, backorder open) and `payment.recheck_required` never fires from backorder edits because `amountChanged = false` for them
- **Cash/card mark-paid is gated to `status = READY`.** `OrderPaymentService.markPaid` rejects with 400 when `paymentType ∈ {CASH, CARD}` and `order.status !== READY`. Bank orders (`BANK_PREPAYMENT`, `BANK_POST_PAYMENT`) accept any status — that's the prepay vs post-pay distinction. `POST /orders` `paymentStatus='paid'` is bank-only at create time for the same reason (a brand-new order is in DRAFT, not READY)
- **Cash/card PAID orders are READY-locked on both edges.** Mark-paid is gated to `status = READY` (above) and `OrderTransitionService` blocks `READY → IN_COLLECTION` / `READY → PARTIAL` for cash/card PAID orders. Together these mean a cash/card order carries `paymentStatus = PAID` exclusively while in `READY` (or `COMPLETED` after the forward transition). Don't write code that pattern-matches on cash/card PAID + a non-READY/non-COMPLETED status — that combination cannot exist via the normal API. Bank orders carry no such invariant (`BANK_PREPAYMENT` legitimately holds PAID at DRAFT/CONFIRMED, etc.)
- `Order.totalAmount`, `OrderItem.*Price` / `quantity`, and `Branch.deliveryThreshold` are TypeORM `numeric` columns → returned as **strings**. Use `Number.parseFloat` when computing, format back with `.toFixed(N)` matching the column's scale. Current scales: `OrderItem.originalPrice` = `numeric(18,0)`, `OrderItem.discountedPrice` = `numeric(18,2)`, `OrderItem.quantity` = `numeric(18,3)`, `Order.totalAmount` = `numeric(18,2)`, `Branch.deliveryThreshold` = `numeric(18,0)`, `Customer.discountPercent` = `numeric(5,2)`. Postgres rounds half-to-even on insert if the input has more fractional digits than the scale
- `PaymentTypeEnum` and `PaymentTermsEnum` have identical members today but live in separate enums — `Order.paymentType` is copied from `Customer.paymentTerms` via an `as unknown as` cast in `OrdersService.create`. If the enums diverge, resolve intent explicitly rather than widening the cast
- `TypeOrmExceptionFilter` maps `23505 → 409`, `23503 → 409`, `22P02 → 400`, `42P01 → 503`. If you catch a driver error locally, you're bypassing this filter — prefer letting it bubble
- All scheduled-job times are **Asia/Tashkent** (UTC+5). Use an explicit timezone when configuring BullMQ cron; don't rely on host TZ
- Product search tokenizes the query on whitespace (tokens shorter than 2 chars dropped) and AND-combines per-token clauses, **routed by token shape**: SKU-shaped tokens (regex `SKU_TOKEN_PATTERN` — `^[A-Za-z0-9-]+$` with ≥1 digit) run `(sku ILIKE OR barcode ILIKE OR name_expr ILIKE)` (literal substring, no fuzzy); all other tokens run `(name_expr ILIKE OR strict_word_similarity > 0.4)` over Cyrillic/Latin transliteration variants. The routing matters: running `strict_word_similarity` on a numeric token will fuzzy-match numeric *words* inside product names (`'00002'` vs the word `'000'` scores ~0.5), so numeric tokens deliberately skip the fuzzy path. Use `strict_word_similarity`, **not** `word_similarity` — the strict variant bounds the matched extent to word boundaries on name tokens. Ranking sums the best per-token `strict_word_similarity` over name tokens only; if every token is SKU-shaped (no score), order by `sku ASC`. The pg_trgm extension must be installed in the target DB — check before running a fresh migration. No GIN trgm index yet; at ~10k SKUs the seq scan is acceptable but watch latency as the catalog grows — adding `CREATE INDEX … USING gin ((coalesce(name->>'uz','') || ' ' || coalesce(name->>'ru','')) gin_trgm_ops)` will accelerate the ILIKE leg of the search (the function-call form of (`strict_`)`word_similarity` is not indexable without a session-level threshold). **Locale gotcha:** `strict_word_similarity` word-boundary detection depends on libc `isalnum`/`isspace` (i.e. on `LC_CTYPE` of the database). Local-vs-prod result divergence on the same code + same data is almost always a `datctype` mismatch (e.g. macOS `en_US.UTF-8` vs Alpine `C.UTF-8`); compare `pg_database.datctype` and `show_trgm(<sample>)` between environments before debugging the SQL
- `RolesGuard` checks role only; **branch-scoped** permission checks are not yet implemented. Don't assume `@Roles(UserRole.STORE_MANAGER)` means "store manager for this branch"
- The `/socket` namespace uses **websocket-only transport** (no HTTP-polling fallback) — a strict WebSocket-blocking proxy will fail to connect. Acceptable for the internal admin dashboard
- Redis pub/sub is the **delivery** channel, not persistence — Redis does not retain events. Offline / disconnected users catch up via `GET /notifications` and `GET /notifications/unread-count` on next page load. Don't try to replay missed events from Redis
- **All non-`BASIC` users currently receive every order event** via the global `orders:all` room. Branch-scoped order rooms are deferred until the HTTP role gates pick up branch scope (see "Realtime" API section). This means a `STORE_MANAGER` can today see order events from other branches over the socket (not over the HTTP API). The `OrderSocketPayload` already carries `branchId` so the eventual transition to branch-scoped rooms will not require a payload change
- `PATCH /notifications/:id/read` takes the **`NotificationRecipient.id`** (per-user delivery row), not the shared `Notification.id`. Each user has their own row with their own `readAt`; reading via the shared notification id would require composite lookups everywhere
- `RedisSocketIoAdapter` reads `redis.host` / `redis.port` via `ConfigService.getOrThrow` — boot fails fast if those env vars are missing. The adapter creates two `ioredis` clients (`pubClient` + `pubClient.duplicate()` for sub) with `lazyConnect: false` and `maxRetriesPerRequest: null` (the latter is required by the Socket.IO Redis adapter's blocking subscriber semantics)
- Jest resolves the `@common/*` path alias via `moduleNameMapper` in [package.json](package.json) (mirroring the `tsconfig.json` `paths` entry). When adding a new top-level alias, update both

## Changelog

Newest first. See "Maintaining This File" for what counts as a logged change.

### 2026-05-07 (later 2)

- **NEW** `POST /orders/:id/transitions` — added `PARTIAL → IN_COLLECTION` reverse path (roles `ADMIN`, `STORE_MANAGER`, `SALES_MANAGER`). No payload required; optional `pickerId` reassigns. Mirrors the existing `READY → IN_COLLECTION` reverse semantics: existing `BACKORDERED` items are preserved (picker resolves via `PATCH /orders/:id/items/:itemId` from `IN_COLLECTION`), `pickerId` is retained when no payload, audit `STATUS_CHANGE` with `diff: null`, the existing `order.assigned_to_picker` notification fires for the (current or reassigned) picker. **Why:** operators need to undo a premature `IN_COLLECTION → PARTIAL` declaration (or recover when all backorders cleared mid-flow before READY) without going through `PARTIAL → CANCELLED` or waiting on every backorder to resolve before forcing `PARTIAL → READY`. The forward `IN_COLLECTION → PARTIAL` rule (`≥1 BACKORDERED item`) still applies, so an order with backorders intact bounces back to PARTIAL on demand — no information lost. **Implementation:** added `IN_COLLECTION` to `ALLOWED_ORDER_TRANSITIONS[PARTIAL]` and a `partial->in_collection` entry to `ORDER_TRANSITION_ROLES` in [orders.constants.ts](src/common/constants/orders.constants.ts); widened the no-`pickerId` branch in `applyTransitionSideEffects` to accept `from ∈ {READY, PARTIAL}` in [order-transition.service.ts](src/orders/internal/order-transition.service.ts). The picker-reassignment branch was already from-agnostic, so passing `pickerId` works the same way it does on `READY → IN_COLLECTION`. The cash/card-PAID reverse-block from earlier today is unaffected: it's keyed on `from === READY`, and cash/card PAID + PARTIAL is unreachable in the first place (cash/card mark-paid is gated to READY). No DTO, schema, enum, notification-recipient, or migration change.

### 2026-05-07 (later)

- **CHANGED** Reverse READY transitions are now blocked for PAID cash/card orders. `OrderTransitionService.transition` rejects `READY → IN_COLLECTION` and `READY → PARTIAL` with 400 (`READY → <to> is blocked for PAID cash/card orders. Unmark paid first via POST /orders/:id/unmark-paid`) when `paymentStatus = PAID` and `paymentType ∈ {CASH, CARD}`. Bank orders (`BANK_PREPAYMENT`, `BANK_POST_PAYMENT`) are exempt — `BANK_PREPAYMENT` legitimately holds PAID at DRAFT/CONFIRMED, so a paid bank order in `IN_COLLECTION` / `PARTIAL` is a normal lifecycle state. `READY → COMPLETED` is unchanged (still gated on `paymentStatus = PAID` for every paymentType). The new gate sits in `OrderTransitionService.transition` immediately after the existing `READY → COMPLETED` PAID check at [order-transition.service.ts:73-81](src/orders/internal/order-transition.service.ts#L73-L81); it reuses the existing [`OrderPaymentPolicy.isBankPayment`](src/orders/internal/order-payment.policy.ts) helper that `OrderPaymentService.markPaid` already uses for the symmetric mark-paid gate. **Why:** cash/card mark-paid is gated to `status = READY`, so allowing the reverse paths would park a cash/card order in a state where the mark-paid endpoint itself wouldn't accept it (an inconsistent paid + pre-READY state). Cash has been physically collected and cards have been charged, so there's no business reason to flip back without an explicit unmark step. Recovery from a premature READY mark on a paid cash/card order goes through ADMIN `POST /orders/:id/unmark-paid` → revert → re-mark via `POST /orders/:id/mark-paid` once back in READY (mirrors the existing two-step recovery for basket edits on a PAID order). **Constructor change:** `OrderTransitionService` now injects `OrderPaymentPolicy` as a 6th parameter; `OrdersModule` already registered the policy as a provider for `OrderPaymentService`, so DI required no module-level change. **Test impact:** [orders.service.spec.ts](src/orders/orders.service.spec.ts) `setupTransition` helper updated to pass an `OrderPaymentPolicy` instance; four new specs cover cash + card PAID rejection on both reverse paths and bank PAID + cash PAID happy paths through the forward `READY → COMPLETED` transition. No schema, enum, DTO, role-gate map, `ALLOWED_ORDER_TRANSITIONS`, notification-recipient, or migration change.

### 2026-05-07

- **CHANGED** Relaxed the PAID-order item-edit lock. `POST /orders/:id/items` and `DELETE /orders/:id/items/:itemId` still 400 on a PAID order (basket composition is locked). `PATCH /orders/:id/items/:itemId` now accepts backorder-only payloads — `status`, `backorderedQuantity`, and `notes` riding along — while a PAID order is in `CONFIRMED`, `IN_COLLECTION`, or `PARTIAL`; only payloads that send `quantity` are still 400'd (`Item quantity cannot be changed while the order is PAID; backorder status edits are still allowed.`). **Why:** an item that was AVAILABLE at mark-paid can become BACKORDERED when the picker hits an empty shelf, and a BACKORDERED line can resolve to AVAILABLE when the warehouse delivers. Neither flips `quantity`, neither moves `totalAmount`, and the customer's payment is still good for the original basket — forcing an `unmark-paid` round-trip for every stock-state change is friction with no business value. **Implementation:** new helper `OrderLineService.assertQuantityNotChangedWhilePaid(order, quantity)` ([order-line.service.ts](src/orders/internal/order-line.service.ts)) replaces the `assertNotPaid` call inside `OrderDetailsMutationService.updateItem` only — `addItem` and `deleteItem` keep their hard `assertNotPaid` gate. The audit + notification pipeline is unchanged: `applyTotalAndPaymentDiff` is a no-op when `quantity` is unchanged, so `amountChanged = false` and `payment.recheck_required` is suppressed naturally; `backorder.updated` (SCM) still fires on `status`/`backorderedQuantity` changes. `paymentStatus` stays `PAID` throughout backorder edits. `POST /orders/:id/unmark-paid` remains the only path to change `quantity` or basket composition on a paid order.

### 2026-05-06

- **BREAKING / NEW** Tightened payment + confirm gates on orders. Three behavior changes plus one new endpoint, no schema migration.
  - **Cash/card mark-paid now gated to `status = READY`.** `OrderPaymentService.markPaid` rejects with 400 when `paymentType ∈ {CASH, CARD}` and `order.status !== READY`. Bank orders (`BANK_PREPAYMENT`, `BANK_POST_PAYMENT`) keep their any-status mark-paid behavior — bank prepayment is typically marked at DRAFT/CONFIRMED, post-payment later. The status check sits between the existing `already PAID` short-circuit and the `resolveMarkPaidRoles` role check in [order-payment.service.ts:46-53](src/orders/internal/order-payment.service.ts#L46-L53).
  - **`POST /orders` `paymentStatus='paid'` is now bank-only.** Cash/card creates with the field set return 400 (`Cash/card orders cannot be created with paymentStatus=paid; mark PAID after the order reaches READY`). The bank role gate (`ADMIN` / `ACCOUNTANT`) is unchanged for bank creates. Reasoning: a freshly-created order is in DRAFT, not READY, so there's no consistent path for cash/card pre-marking. Implementation in [order-creation.service.ts:67-79](src/orders/internal/order-creation.service.ts#L67-L79).
  - **PAID orders are now immutable except for endDate.** `OrderLineService.assertNotPaid(order)` is called after `assertOrderDetailsEditable` in `addItem` / `updateItem` / `deleteItem`; PAID orders return 400 (`Order items cannot be changed while the order is PAID; unmark paid first via POST /orders/:id/unmark-paid`). - **CHANGED** `GET /products` — `search` tokens are now **routed by shape**. SKU-shaped tokens (regex `SKU_TOKEN_PATTERN` — `^[A-Za-z0-9-]+$` with ≥1 digit, e.g. `00002`, `162000001-00100`) match `product.sku ILIKE '%token%'` OR a literal-substring ILIKE on the concatenated name expression — they deliberately skip `strict_word_similarity`.
